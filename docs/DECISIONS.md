### 가드레일 실패 처리 (2일차)
**선택:** 처음 실패하면 부족한 점을 알려 주고 **한 번 다시 조사**한다. 그래도 실패하면 **'의심'으로 낮추고** 사람 검토 표시(`needs_review`)를 남긴다. (`guardrail_on_fail="retry"`, `max_guardrail_retries=1`)

**검사 두 가지** (`guardrail.py`)
| 검사 | 기준 | 실패 시 문제 설명 |
|---|---|---|
| G-1 근거 존재 | 판정이 인용한 `event_id`가 도구로 조회한 `seen_event_ids` 또는 알림의 `event_ids`에 있어야 한다 | `조회하지 않은 근거: evt-...` |
| G-2 악성 근거 2개 | `malicious`이면 서로 다른 근거 id가 2개 이상 (같은 id 중복은 1개로 침) | `악성 판정에는 서로 다른 근거가 2개 이상 필요합니다 (현재 N개)` |

**왜 이렇게 했나**
- 곧바로 낮추면 도구를 더 불러 보면 확인될 근거도 버린다. 한 번은 기회를 준다.
- 계속 다시 조사하면 비용과 시간이 끝없이 늘고, 지어낸 근거는 몇 번을 다시 시켜도 사라지지 않을 수 있다. 그래서 재시도는 1회로 막는다.
- 낮출 때 '정상'이 아니라 '의심'으로 두는 이유: 근거를 검증하지 못했다고 해서 안전하다는 뜻은 아니기 때문이다. 사람이 보도록 표시를 남긴다.
- 재조사에도 전체 도구 실행 6라운드 제한은 그대로 적용한다 (`ARCHITECTURE.md` "확정" 참고).

**확인 (가짜 LLM '거짓말쟁이', `fabricate=True`)**
- 경로: 조사 → 도구 → 조사 → 판정 → 가드레일(실패) → 조사 → 판정 → 가드레일(실패) → 권고 → 승인 → 리포트
- 결과: 지어낸 `evt-fabricated-0001`이 빠지고 판정은 `suspicious`, `needs_review: True`, 근거는 알림의 `evt-00000023` 하나만 남는다.
- `pytest tests/test_guardrail.py` 4개 통과.

**한계 (아직 안 잡는 것)**
- 두 검사는 id가 실제로 있는지만 본다. 인용한 기록이 판정 이유와 **관련 있는지**는 확인하지 못한다.
- 알림의 `event_ids`는 조회하지 않아도 확인된 기록으로 친다. 알림 자체가 틀렸으면 이 검사로는 못 잡는다.

### 프로브 설계표 (2일차, 인프라 4단계)

API는 외부 요청을 받는 창구이고, 워커는 새 알림을 스스로 가져가 분석하는 작업자다. 아래는 4단계 초기 배포에 적용한 설계이며, 실제 처리 시간과 장애 실험 결과를 보고 조정한다.

| | API | 워커 |
|---|---|---|
| liveness | 포트 8000의 `/healthz`로 API가 응답하는지 확인한다. DB 연결 여부는 검사하지 않아 외부 DB 장애 때문에 API를 반복 재시작하지 않도록 한다. | 포트 9100의 `/healthz`로 작업 루프의 마지막 하트비트를 확인한다. 오래 갱신되지 않으면 비정상으로 판단한다. 단, 정상적인 장시간 분석과 구분하도록 아래 제한을 고려한다. |
| readiness | 포트 8000의 `/readyz`로 OpenSearch·Postgres 연결을 확인한다. 실패하면 Service의 요청 전달 대상에서 제외한다. | 현재 구조에서는 생략한다. 외부 요청을 받지 않고 스스로 알림을 가져오므로, readiness 실패만으로 알림 가져오기가 자동 중단되지 않는다. |
| 종료 유예 | 우선 기본값 30초를 사용한다. 긴 분석 요청이 있다면 실제 처리 시간을 보고 조정한다. | 초기 `terminationGracePeriodSeconds: 120`을 적용한다. 종료 요청 후 새 알림을 가져오지 않고 처리 중인 알림을 마칠 시간을 준다. 120초 안에 모든 작업이 완료된다는 보장은 아니다. |

**적용값과 확인할 사항**
- 현재 `heartbeat_stale_sec` 기본값은 60초이고, 워커는 작업 루프 시작 시에만 하트비트를 갱신한다. 알림 분석 중에는 갱신하지 않아 정상적인 LLM 분석이 길어져도 `/healthz`가 실패할 수 있다.
- `41-worker.yaml`에서 `HEARTBEAT_STALE_SEC=180`으로 기본값을 덮어쓴다. liveness는 10초 간격·timeout 3초·연속 실패 3회이며, startupProbe는 10초 간격·timeout 3초·실패 30회를 허용한다. 종료 유예 120초는 하트비트 제한과 별개의 설정이다. 정상 분석이 길어지는 경우의 오탐 재시작 가능성은 여전히 남아 있으므로 실제 LLM 전환 후 재평가한다.
- 현재 워커는 SIGTERM을 받으면 종료 플래그를 설정하고, 진행 중인 처리가 끝난 뒤 루프를 종료한다. 유예 시간을 넘겨 강제 종료되는 경우 체크포인트·알림 lease에 따른 복구 동작은 깨 보기 4-5에서 별도로 확인한다.
- 서버 적용 결과: 생성기와 워커 rollout 성공. 생성기의 기록 저장과 워커의 `completed`·`pending_approval` 처리를 로그로 확인했고, 미처리 알림 `status=new` 조회 결과는 0건이었다. 현재 mock 도구·가짜 LLM 기반 흐름 검증이며, 실제 분석 품질 검증 및 깨 보기 4-3·4-5는 별도 진행한다.
